# LF5.6.2: Of Verification & Validation (V-Model)

## User Story

As a Quality Manager, **I** want to understand the V-Model, so that **I** can ensure every development phase is strictly paired with a corresponding testing phase.

## Celebration Criteria

- **I can define** the concepts of Verification and Validation. (K1)
- **I know how to map** development phases to testing phases in a V-shape. (K3)
- **I can explain** why the V-Model requires early test planning. (K2)

## Knowledge Briefing

The V-Model (V-Modell XT is the standard for German public IT projects) is an extension of the Waterfall model. It bends the linear waterfall into a "V" shape to emphasize quality assurance.

**1\. The Left Side (Verification - Building the system right):** Deals with decomposition and design.

- Requirements Analysis
- System Design
- Architecture Design
- Module Design

**2\. The Bottom (Coding):** The actual implementation of the code.

**3\. The Right Side (Validation - Building the right system):** Deals with integration and testing.

- Unit Testing (Tests the Module Design)
- Integration Testing (Tests the Architecture Design)
- System Testing (Tests the System Design)
- User Acceptance Testing / UAT (Tests the Requirements Analysis)

## Common Pitfalls

- Confusing Verification and Validation.
  - **Verification:** "Are we building the product _right_?" (Does the code match the technical blueprint?).
  - **Validation:** "Are we building the _right_ product?" (Does it actually solve the customer's real-world problem?).
